## NTC Micro-Harness: Atomic Engineering Protocol & Plugin (Microservices Edition v2.1)

Start with the requested outcome and use the repository as the single system of record.
Read `docs/WORKFLOW.md` and only the relevant discovery docs (`PRD.md`, `ARCHITECTURE.md`), `SPEC.md`, module spec, skill map, UI prototype, phase dossier, code, and validation material.

### Core Operating Invariants

1. **Hierarchy of Truth & Documents** (a lower document must never contradict a higher one; on conflict, STOP and ask):
   - `PRD.md` & `ARCHITECTURE.md`: Product Requirements & System Architecture Blueprint created via interactive discovery in **Step 1 (`/ntc-init`)**.
   - `docs/prototypes/registry.md` & `docs/prototypes/<module-slug>/scr-<nn>-*.html`: The Visual & UI Prototype Contract Registry (when `UI Required: YES`) — generated from `PRD.md` & `ARCHITECTURE.md` and approved (`APPROVED`) in **Step 2 (`/ntc-prototype`)** with locked design tokens, visual states (`default`, `loading`, `empty`, `error`), and `data-testid` anchors (`SCR-<MOD>-<NN>`).
   - `SPEC.md`: The supreme overall system specification synthesized and locked in **Step 3 (`/ntc-spec`)** from `PRD.md`, `ARCHITECTURE.md`, and the approved UI prototypes.
   - `AGENTS.md`: The mandatory operating contract, behavioral boundaries, and execution rules.
   - `docs/plans/system-roadmap.md`: The Project Roadmap — architecture blueprint, Module Registry, Global Phases (`SYS` opening and closing E2E bookends), inter-module dependency graph, **Active Work Pointer**, and **Change Request (`CR-<NN>`) Log**.
   - `docs/plans/contract-registry.md`: The Cross-Module Contract Registry — every inter-module API, event, and shared schema (`CT-<PROVIDER>-<NN>`) with provider, consumers, spec path, version, and status.
   - `ai-skill-maps.md`: The Project AI Skill Playbook — created in **Step 3 (`/ntc-spec`)** right after locking `SPEC.md`; maps every module/service and phase to mandatory local skills (`.agents/skills/<skill-name>/SKILL.md`) that the agent MUST read before writing detailed module specs, WBS plans, or production code.
   - `docs/modules-spec/<module-slug>.md`: The Detailed Module Specification — created in **Step 4 (`/ntc-modules`)** using `SPEC.md`, `ai-skill-maps.md`, `docs/plans/contract-registry.md`, and `docs/prototypes/registry.md`; defines scope, user stories, exact DB/storage DDL schemas, contracts (`CT-*`), UI screen mappings (`SCR-*`), business flows/state machines, Given/When/Then acceptance criteria, error codes, and the **Module Phase Sequence** (`<MOD>-P<NN>`).
   - `docs/plans/active/<module-slug>/phase-<NN>-<slug>.md`: Pre-generated Module Phase Dossiers (**Step 5 / `/ntc-plan`**) containing Major Tasks, Atomic Work Breakdown Structure (WBS), UI Prototype References, and the real-time `🎫 Resume Ticket`.
   - `docs/plans/completed/<module-slug>/phase-<NN>-<slug>.md`: Verified, archived dossiers (immutable audit record).
   - **Human-Only Boundary (`STEP-by-STEP.md`):** The root `STEP-by-STEP.md` file is generated at the end of **Step 4 (`/ntc-modules`)** strictly for the **Human Architect** to read and copy prompts/commands from. **AI Agents MUST NOT read `STEP-by-STEP.md` during execution.**

2. **The 6-Step `/ntc-*` Gated Lifecycle (NEVER skip steps/gates):**
   - **Step 1 (`/ntc-init`) — Git Remote Connection, Interactive Requirements Q&A → `PRD.md` & `ARCHITECTURE.md`:**
     - **Step 1.0 (Git Repository Setup First):** Before doing anything else, ask the user to input the **Project Git Repository URL** (optional — may be left blank for local-only) along with their basic project requirements. Ensure `git init` is initialized in the workspace and, if a repository URL is provided, connect `git remote add origin <repo-url>` (or `git remote set-url origin <repo-url>`) immediately. Ensure the Harness directory structure (`docs/`, `scripts/validate_plans.py`, `AGENTS.md`) is bootstrapped.
     - **Step 1.1 (Interactive Discovery Q&A):** Based on the user's initial requirements, ask 3–5 concise clarifying questions (user roles/RBAC, core workflows, tech stack, database, `UI Required: YES | NO`, scale/security constraints) so the user can refine the requirements.
     - **Step 1.2 (Generate & Lock `PRD.md` + `ARCHITECTURE.md`):** Instantiate `PRD.md` (from `docs/templates/prd-template.md`) and `ARCHITECTURE.md` (from `docs/templates/architecture-template.md`). Present them for user review and approval before advancing to Step 2. **NEVER start writing production code.**
   - **Step 2 (`/ntc-prototype`) — Interactive UI Prototyping from `PRD.md` & `ARCHITECTURE.md` (Conditional if UI):**
     - If the system has no UI (`UI Required: NO` in `PRD.md`), set `> **UI Required:** NO` in `docs/prototypes/registry.md` and proceed directly to Step 3 (`/ntc-spec`).
     - If the system includes any UI/Frontend module (`UI Required: YES`), use `PRD.md` and `ARCHITECTURE.md` to populate `docs/prototypes/registry.md` (from `docs/templates/ui-prototype-registry-template.md`) with locked Design Tokens and the UI Screen Inventory (`SCR-<MOD>-<NN>`), and generate self-contained interactive HTML/CSS prototypes at `docs/prototypes/<module-slug>/scr-<nn>-<slug>.html`.
     - Every prototype HTML file MUST cover all required visual states (`default`, `loading`, `empty`, `error`) and include `data-testid="scr-<nn>-<element>"` attributes on key layout containers, forms, inputs, tables, and action buttons.
     - **Hard Stop for Visual Approval:** Iterate on the prototypes with the Human Architect (`/ntc-prototype --revise "..."`) until satisfied. **DO NOT proceed to Step 3 until the Human Architect approves (`--approve`) and all active screens in `docs/prototypes/registry.md` are marked `APPROVED`.** *(Self-contained reference HTML prototypes in `docs/prototypes/` are the ONLY code permitted before Step 6 / Gate 5).*
   - **Step 3 (`/ntc-spec`) — Overall `SPEC.md`, Roadmap, Contracts & Skill Playbook (`ai-skill-maps.md`):**
     - **Step 3.1 (Synthesize & Lock Overall `SPEC.md` + Roadmap + Contracts):** Based on the approved `PRD.md`, `ARCHITECTURE.md`, and approved UI Prototypes (`docs/prototypes/registry.md`), generate the overall `SPEC.md` (from `docs/templates/spec-template.md`), `docs/plans/system-roadmap.md` (Module Registry with `SYS` opening foundation and `SYS` closing E2E bookends, Global Phases, Dependency Graph), and `docs/plans/contract-registry.md` (`CT-*`). Present to the user to review and lock.
     - **Step 3.2 (Skill Discovery & `ai-skill-maps.md` per Module/Service):** Immediately after locking `SPEC.md`, use the registered modules/services in `SPEC.md` and `system-roadmap.md` to propose corresponding AI skills for each function (module/service). Ask the user for skill search URLs/repositories (e.g., `https://skillsmp.com/search`, `https://felo.ai/vi/skills`, GitHub) if needed, and propose a candidate skill table (including `atomic-harness-gatekeeper`, `<project>-domain-invariants`, and `ui-prototype-fidelity` if UI). **Only after user approval**, install the skills into `.agents/skills/` and instantiate `ai-skill-maps.md` (from `docs/templates/ai-skill-maps-template.md`).
   - **Step 4 (`/ntc-modules`) — Detailed Module Specifications (`docs/modules-spec/<slug>.md`) & `STEP-by-STEP.md`:**
     - **Step 4.1 (All Detailed Module SPECs using `SPEC.md` + `ai-skill-maps.md` + `Prototypes`):** For every registered module in `docs/plans/system-roadmap.md`, **first read its mapped skills in `ai-skill-maps.md` (`.agents/skills/<skill>/SKILL.md`)**, then combine with `SPEC.md`, `docs/plans/contract-registry.md`, and `docs/prototypes/registry.md` (`SCR-<MOD>-<NN>`) to instantiate `docs/modules-spec/<module-slug>.md` (from `docs/templates/module-spec-template.md`).
     - **Step 4.2 (User Approval & `STEP-by-STEP.md` Generation):** Present `docs/modules-spec/*.md` to the Human Architect for review and approval (`--approve`). Immediately upon approval, instantiate `STEP-by-STEP.md` (from `docs/templates/step-by-step-template.md`) containing the dependency execution order, `/ntc-*` commands, and copy-paste prompts.
   - **Step 5 (`/ntc-plan` — Gate 4: Full Phase Dossiers & Level-4 WBS Pre-Generation):**
     - Consult `ai-skill-maps.md`, read the required `.agents/skills/<skill>/SKILL.md` files, and instantiate **ALL Phase Dossiers** (`docs/plans/active/<module-slug>/phase-<NN>-<slug>.md` from `docs/templates/phase-dossier-template.md`) for **ALL modules in the entire project**.
     - Decompose every phase into Major Tasks (`<MOD>-P<NN>.<M>`) and **Atomic Tasks (Level 4 - Micro-tasks: `<MOD>-P<NN>.<M>.<A>`)**. For UI modules, every UI Atomic Task MUST explicitly link its `UI Prototype Reference` (`SCR-<MOD>-<NN>` -> `docs/prototypes/<module-slug>/scr-<nn>-*.html`).
     - **Gate 4 Exit Lock:** Code implementation (Step 6 / Gate 5) is strictly forbidden until **every planned phase of every module** has its Phase Dossier generated in `docs/plans/active/`, all UI prototypes in `docs/prototypes/registry.md` are `APPROVED`, `python scripts/validate_plans.py` passes with 0 errors, and the user approves Step 5.
   - **Step 6 (`/ntc-run` / `"Tiếp tục"` — Gate 5: Atomic Implementation & State Machine):**
     - Begin code implementation ONLY after Step 5 (Gate 4) is complete and the user invokes `/ntc-run` or `"tiếp tục"`.

3. **Implementation Invariants (Strict Execution at Step 6 / Gate 5):**
   - **Single Atomic Task Turn (1 Turn = 1 Task):** In any single response, execute **ONLY ONE ATOMIC TASK** (`<MOD>-P<NN>.<M>.<A>`). Never implement multiple tasks, modules, or phases at once.
   - **Skill Activation Invariant:** Before implementing a module's phase, read the mandatory skills listed for that module/phase in `ai-skill-maps.md`.
   - **Single-Module Scope & Multi-Agent Isolation:** An atomic task modifies only its own module's `Code Root` and that module's dossier in `docs/plans/active/<module-slug>/`. Parallel agents (across tabs, subagents, or isolated Git Worktrees) may execute independent modules simultaneously once shared contracts (`CT-*`) are `AVAILABLE`.
   - **Contract-First (Module & Cross-Module):** Task `.1` of any Major Task MUST define Types, Interfaces, Schemas, DTOs, or Protobufs before business logic. Every cross-module contract in `docs/plans/contract-registry.md` must be codified at its spec path (status `AVAILABLE`) before consumer/provider integration logic is written.
   - **UI Prototype 1:1 Parity Invariant (Strict Visual Lock for UI Tasks):** When executing any Atomic Task that references a UI Prototype (`SCR-<MOD>-<NN>`), the agent MUST `read_file` the corresponding `docs/prototypes/<module-slug>/scr-<nn>-*.html` file and `docs/prototypes/registry.md` in that same turn before writing component code. The agent MUST port the approved DOM hierarchy, design tokens, CSS/Tailwind classes, visual states (`default`, `loading`, `empty`, `error`), and `data-testid` attributes **1:1** into the production framework component. Improvising unapproved layouts, altering color/typography tokens, omitting elements, or dropping `data-testid` hooks is strictly forbidden. The Major Task's verification test (Task `.3`) MUST assert the presence of the prototype's `data-testid` anchors and UI states.
   - **Contract & Prototype Change Control:** Changing a registered contract (`CT-*`) or an approved UI prototype (`SCR-*`) bumps its version and logs impacted consumers/screens. Breaking contract changes or visual layout changes require explicit user approval (`docs/prototypes/registry.md` updated first) and a decision record (`docs/templates/decision.md`).
   - **Executable Proof & No-Stubbing Rule:** Every atomic task must be verified with executable proof (unit tests pass, typechecks succeed, or diagnostic logs). Never output incomplete stubs (`// TODO`, `// implement later`).
   - **Atomic Git Commit Checkpointing (Clean Rollback Point per Task):** At the end of every Atomic Task turn in Step 6 (Gate 5) — strictly AFTER the `Executable Proof Command` passes, `- [x]` is checked off, the `🎫 Resume Ticket` is updated, and `python scripts/validate_plans.py --fix` succeeds — the agent MUST stage the module's changes and create an atomic git commit (`git add <code-root> docs/plans/ docs/modules-spec/ && git commit -m "feat(<slug>): complete <MOD>-P<NN>.<M>.<A> - <summary>"`), recording the commit hash in the dossier's Execution Evidence Log. This guarantees that `HEAD` is always a verified checkpoint and any uncommitted diff belongs strictly to an interrupted in-flight task.
   - **Cross-Module Integration & Full-Stack E2E Gate (`SYS` Closing Phase — `/ntc-status --e2e`):** The final Global Phase (`GP-<FINAL>`) MUST execute a closing `SYS` phase (`SYS-P<FINAL>`) after all participating domain and UI modules have completed their phases. This closing `SYS` phase spins up the integrated stack (DB + Backend Services + API Gateway + Frontend), verifies live cross-module contract (`CT-*`) round-trips without mocks, and runs end-to-end (E2E) user flow tests (asserting the locked `SCR-*` `data-testid` anchors from UI click → API → DB persistence → UI state render).
   - **In-Phase Dynamic Amendment vs. Mid-Flight Change Request (`/ntc-cr` / `CR-<NN>`):**
     - *Tier 1 — Local Bug / Edge Case (`<MOD>-P<NN>.<M>.<A>a`):* If an unforeseen bug or edge case is discovered during Step 6 within the current module's scope (no contract `CT-*` or UI screen `SCR-*` changes), insert a sub-task (`<MOD>-P<NN>.<M>.<A>a`) into the active dossier, document the reason, and execute it atomically.
     - *Tier 2 — Mid-Flight Change Request (`CR-<NN>` via `/ntc-cr "<mô tả>"` or `"yêu cầu thay đổi: ..."`):* When the user requests a new feature, new/modified UI screen (`SCR-*`), or cross-module contract change (`CT-*`) during Step 5/6, NEVER rewrite or uncheck completed tasks/dossiers. Execute the **4-Step Delta Reverse-Unlock Protocol**: (1) Log `CR-<NN>` in `docs/plans/system-roadmap.md` (`## 6. Change Request (CR) Log`) and audit impacted modules/contracts/screens; (2) Update/approve only the delta UI prototypes (`SCR-*` in `docs/prototypes/`) and delta contracts (`CT-*` in `docs/plans/contract-registry.md`); (3) Append delta requirements to `SPEC.md` and impacted `docs/modules-spec/<slug>.md` files; (4) Append new Major/Atomic Tasks to active dossiers or generate a new Delta Phase Dossier (`phase-<NN+1>-cr-<nn>-*.md` in `docs/plans/active/<slug>/` if previous phases were already archived in `completed/`), run `python scripts/validate_plans.py --fix`, and resume Step 6 execution via `/ntc-run` or `"tiếp tục"`.

4. **The `/ntc-run` / `"Tiếp tục"` State Machine, Crash Recovery & Archival Engine:**
   - **Write-Ahead & End-of-Turn Checkpointing:** Mark the `🎫 Resume Ticket` as `IN_PROGRESS` with the target Atomic Task ID **before** editing code, and update it with verification results, line numbers, git commit hash, and the **Immediate Next Atomic Action** before yielding any turn. Run `python scripts/validate_plans.py --fix` whenever phase status or focus changes.
   - **3-Step Crash / Dirty-State Recovery (Backed by Atomic Git Commits):** Because every completed `[x]` Atomic Task is immediately committed to `HEAD`, any uncommitted modification in `git status` / `git diff HEAD` belongs exclusively to the interrupted in-flight Atomic Task. Whenever resuming via `/ntc-run` or `"tiếp tục"` (or `"continue"`), NEVER trust the `🎫 Resume Ticket` blindly. Inspect: (1) the first unchecked `- [ ]` Atomic Task in the active dossier, (2) `git status --short` / `git diff HEAD` inside the module's `Code Root`, and (3) `git log -1` vs. target files on disk:
     - *If target files were modified by an interrupted turn and tests already PASS:* check off `[x]`, update the `🎫 Resume Ticket`, create the missing atomic git commit for that task, report recovery, and execute the next unchecked Atomic Task.
     - *If target files are partially written or failing tests from a mid-turn crash:* report the exact interrupted file/line in 3 lines and finish that exact Atomic Task without duplicating code (or restore corrupted lines from `HEAD` before re-applying cleanly).
   - **Sequential `/ntc-run` / `"Tiếp tục"` Execution:** When the active phase has remaining unchecked `- [ ]` Atomic Tasks and the user inputs `/ntc-run` or `"tiếp tục"` (or `"continue"`, `"tiếp tục <MOD>"`), automatically execute the **next sequential unchecked Atomic Task** in that phase.
   - **Final Task of a Phase & Phase Boundary Hard Stop:**
     - On the turn that completes the **final** Atomic Task of a phase (`<MOD>-P<NN>`), check off `[x]`, set `Lifecycle Status` to `PHASE_COMPLETED`, and announce: *"Đã hoàn thành toàn bộ Atomic Tasks của Phase `<MOD>-P<NN>`. Vui lòng nhập `/ntc-run --phase <MOD>-P<NN+1>` (hoặc `tiếp tục phase <MOD>-P<NN+1>`) để lưu trữ phase hiện tại và chuyển sang phase kế tiếp."*
     - **Hard Stop Guardrail:** When a phase has 0 unchecked tasks left (`PHASE_COMPLETED`), if the user inputs plain `/ntc-run` or `"tiếp tục"`, **DO NOT** advance to the next phase. Report that `<MOD>-P<NN>` is out of tasks and require the explicit command `/ntc-run --phase <MOD>-P<NN+1>` or `"tiếp tục phase <MOD>-P<NN+1>"`.
   - **Automatic Phase Transition (`/ntc-run --phase <MOD>-P<NN+1>` or `"tiếp tục phase <MOD>-P<NN+1>"`):** When the user explicitly inputs `/ntc-run --phase <MOD>-P<NN+1>` or `"tiếp tục phase <MOD>-P<NN+1>"`, in that single turn the agent MUST:
     1. Move the completed dossier from `docs/plans/active/<module-slug>/phase-<NN>-*.md` to `docs/plans/completed/<module-slug>/phase-<NN>-*.md`.
     2. Activate `docs/plans/active/<module-slug>/phase-<NN+1>-*.md` (`Lifecycle Status: IN_PROGRESS`) and run `python scripts/validate_plans.py --fix` to synchronize `docs/modules-spec/<module-slug>.md` and the `Active Work Pointer` in `docs/plans/system-roadmap.md`.
     3. Immediately execute the **first Atomic Task (`<MOD>-P<NN+1>.1.1`)** of the newly activated phase.
